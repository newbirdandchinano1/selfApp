1. 表现层（UI / View 层）—— 只管“长什么样、怎么交互”
包含什么：页面（Pages / Screens）、基础组件（Button、Modal、Card、EmptyState）、页面级布局。

职责：接收数据渲染界面，把用户的点击、输入、滑动等事件抛出去。

降耦关键：不直接发网络请求，不写复杂业务规则。组件尽量变成“傻瓜组件”——给它什么数据，它就画什么；用户点了什么，它只调用传进来的回调函数。

--- 第1步覆盖评估（selfApp 现状）---
范围：凡属“画界面 + 抛事件”的文件；不含业务 Hook / Store / API / repository。
切分规则（按页体量，一次对话/PR 只做 1 个子步）：
  · ≤800 行     → 可 1 次做完（抽展示组件 + 断直连仓库）
  · 800～2k     → 拆 2 子步：①纯 UI 区块下沉 ②断网络/仓库，页只留组装
  · 2k～5k      → 按可见区块拆 3～4 子步，每步只动一块 UI
  · >5k         → 按主窗格拆 5～8 子步；禁止一次改整文件
目标：页文件 ideally <300～500 行；仍直连 repository / page-api-fetch / 裸 SQL 则未过关。
入口壳 app/(tabs)/* 已薄，不计入改造工时。

2. 业务层（Domain / Application / Hooks & Store 层）—— 只管“怎么办、状态是什么”
包含什么：业务 Hooks / ViewModels / 状态仓库（Store）/ 业务服务（Service）。

职责：管理页面或模块状态（loading、error、列表数据、筛选条件、表单状态）、协调多个接口调用、做数据清洗/转换（把后端原始字段转成前端好用的格式）、处理业务流转。

降耦关键：它是 UI 和 网络/数据 之间的翻译官与调度员。UI 不直接碰接口，网络层也不关心 UI 怎么显示。

3. 数据与网络层（Data / API / Repository 层）—— 只管“数据从哪来、怎么通信”
包含什么：HTTP 客户端封装、接口定义（API 函数）、请求/响应类型（DTO / Types）、本地缓存读写（LocalStorage / AsyncStorage / DB）。

职责：统一处理 baseURL、鉴权（Token）、请求/响应拦截器、超时与重试、错误码统一转换、缓存策略。

降耦关键：把“怎么请求”和“业务逻辑”隔离开。哪怕以后把 fetch 换成 axios，或者接口路径/字段变了，主要改这一层，业务层和 UI 层几乎不用动。

4. 基础设施 / 公共层（Core / Shared / Utils 层）—— 只管“通用能力”
包含什么：纯工具函数（日期格式化、金额计算、防抖节流）、常量枚举、路由/埋点/日志封装、跨模块通用类型。

职责：提供无业务状态、可随处调用的底层能力。

降耦关键：保持纯粹，不反向依赖业务层，避免出现“工具函数里偷偷 import 某个业务 Store”的循环依赖。

5.验证严格单向依赖（最核心）
规定调用方向只能往下走：

UI 层 可以调 业务层 和 公共层

业务层 可以调 数据/网络层 和 公共层

数据/网络层 只能调 公共层

公共层 尽量不依赖上面任何一层

6.按“业务模块”归拢，而不是把所有文件按类型摊平
小项目按“层”建目录，大一点后如果 components/ 里塞 80 个文件、hooks/ 里塞 60 个文件，依然会乱。更好的方式是“按业务域分块 + 每块内部再分层”（或者公共通用放全局，业务专属放各自模块内）：

通用基础件（按钮、弹窗、请求封装、通用工具）放全局；

某个具体功能（比如“订单”、“聊天”、“设置”）相关的页面、业务 Hook、接口，尽量内聚在自己的模块里，模块之间尽量通过明确的状态或事件通信，少直接互调内部文件。

7.巨文件拆掉
意思是：别让一个文件同时干十件事，把「一万行的 Screen」拆成「薄页面 + 多个小块」。

现在典型问题：TasksScreen.tsx 约 1 万行——里面可能同时有：

列表怎么画、样式、动画
筛选/排序/完成任务的业务规则
直接调 repository、触发同步、发积分


8.关键路径有守卫
意思是：最容易炸、一炸全 App 难受的那几条链路，要有自动检查，别只靠你真机点一遍。
